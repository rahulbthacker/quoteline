---

## 0. Non-negotiables (lessons from the last take-home)

1. **No simulation mode. Ever.** No scripted findings, no seeded "agent results," no `if demo: return canned`. Every extracted value, every flag, every analyst answer comes from a live model call over a real file at request time. The only stub allowed is the SMTP transport.
2. **Nothing hardcoded for the demo questions.** The analyst must answer questions the interviewers invent on the spot. If it cannot, it says so and shows why.
3. **Real files, real mess.** The five vendor replies are real .xlsx, .pdf, .docx, .jpg and .eml files on disk, generated by scripts in `data/gen/`, each deliberately broken in the way the brief describes.
4. **Every number carries provenance.** No value reaches the grid without `source_ref` (file, page or cell or region, verbatim snippet), `confidence`, `model_readings[]`, and `normalization_trace`.
5. **Uncertainty is a state, not a hidden number.** Cell states are `confident | needs_review | not_quoted | overridden`. `not_quoted` is never rendered as 0 or blank. Flagged and not-quoted lines are excluded from every total and from the analyst until resolved, and the UI says so.
6. **LLMs propose, code decides.** Unit conversion, pack-size resolution, FX, line matching, totals, and award rules are deterministic Python with an editable conversion table. The LLM never does arithmetic that lands in the grid.
7. **Every model call is traced.** Model, prompt version, tokens, latency, cost, and (for extraction) agreement score are stored per call and visible in the Run inspector.
8. **A golden set exists and is reported.** Because we fabricate the data, we know the truth. The eval harness reports extraction accuracy per vendor per field, and the note states the number.
9. **Runs from one command on a fresh clone.** `make demo` (or `docker compose up`) seeds the RFx, sends it, ingests the five replies, and opens the UI. Test this on a clean machine before submission.
10. **The one-page note and the recorded walkthrough are deliverables, not afterthoughts.** They are steps in the build order, not things done if time remains.

## 1. What we are building

One flow, end to end, for corrugated packaging:

Draft (co-pilot builds RFx) → Sent (stubbed email) → Responses (five replies ingested) → Compare (normalised grid with provenance) → Review queue (resolve uncertainty) → Analyse (NL over the grid, query shown) → Award (rules, exclusions, audit, sign-off).

Personas: category buyer (primary), VP approver (Analyse and Award, read plus sign-off), technical evaluator (questionnaire scoring), vendor x5 (email in, email out, stubbed), admin (conversion table, FX policy, thresholds; settings page only).

Demo scale: 5 vendors, 30 line items, 8-question questionnaire, 3 attached documents (BRC certificate, MSDS for inks, a sample spec sheet).

## 2. Stack

- **Backend:** Python 3.12, FastAPI, SQLite via SQLAlchemy for app state, DuckDB for the normalised quote table (the analyst queries it), Pydantic for every schema.
- **Frontend:** Vite, React 18, TypeScript, Tailwind v4, shadcn/ui, TanStack Table v8, TanStack Query, Recharts, Lucide, Sonner. Fonts: Geist and Geist Mono via Google Fonts with system fallbacks.
- **Models** (env-configurable, all three keys expected):
  - `EXTRACT_PRIMARY` = Claude Opus 5.5 (`claude-opus-5-5`)
  - `EXTRACT_SECONDARY` = Gemini 3.1 Pro (image and photo reads lead here)
  - `JUDGE` = GPT-5.6 Sol (eval harness only; different family from the extractor)
  - `ROUTER` = Claude Haiku 4.5
  - `ANALYST` = Claude Opus 5.5
  - Fallback chain per role is a config list; a failed call is retried once, then the item is flagged `needs_review` with reason `model_error`, never silently dropped.
- **File parsing:** openpyxl (xlsx), python-docx (docx), pypdf plus page rasterisation via pdf2image for PDF pages sent as images, Pillow for the photo, Python `email` for .eml. Parsers produce text plus layout hints; the model does the reading.
- **Email stub:** an `Outbox` table and an `Inbox` folder watcher. "Send" writes an .eml to `mail/outbox/`. "Receive" ingests any file dropped into `mail/inbox/<vendor>/`. The demo drops the five replies in with one command.
- **Design tokens:** copy verbatim from `design/tokens.css` (light and dark; `color-scheme` declared; dark theme under both `prefers-color-scheme: dark` and `[data-theme="dark"]`). The mockup canvas is the visual reference.

## 4. Data model (the parts that matter)

- **RFx**: id, title, category, base_unit (`per_1000_pcs`), currency (INR), fx_policy {source, rate, as_of}, freight_policy, tax_policy, terms, questionnaire[], line_items[].
- **LineItem**: line_id (L01..L30), description, spec {ply, gsm, dims_mm, print, board_weight_kg_per_pc}, qty, uom, last_year_price_inr (for "rest same as last year").
- **VendorReply**: vendor_id, channel, received_at, files[], format_detected, lines_quoted_count, freight_statement, currency_detected, questionnaire_answers[], attachments[].
- **Extraction** (one per vendor line per model): vendor_id, line_id (nullable until matched), raw_value, raw_unit, raw_currency, source_ref {file, locator, snippet, bbox?}, confidence, model, prompt_version, notes.
- **QuoteCell** (the grid): vendor_id, line_id, state, inr_per_base, raw_display, readings[] (both models), agreement, normalization_trace (ordered steps with factors and sources), flag_reason?, override {value, actor, reason, at}?.
- **ReviewItem**: cell refs, kind (unit_ambiguity | ocr_disagreement | footnote_condition | not_quoted | model_error | outlier | missing_freight), reason text, options[], status.
- **Scenario**: name, filters (quality_pass_only, exclude_vendors[], freight_inclusive), result table, query text, totals.
- **Award**: scenario_id, allocations[], rules_applied[], exclusions[], open_items[], status, approvals[].
- **AuditEvent**: actor (system | user id), action, before, after, at. Immutable.
- **Trace**: call_id, role, model, prompt_version, input_tokens, output_tokens, latency_ms, cost_inr, parent_run_id.

## 5. Agent contracts

All agents return Pydantic-validated structured output. Every prompt file starts with a version header and a one-line purpose. No agent performs arithmetic that reaches the grid.

**Intake co-pilot** (`intake.py`): chat turns → RFx draft. Input: conversation plus category template. Output: RFx schema. Rules: asks for missing fields once, never invents quantities, marks assumptions in `terms.assumptions[]`. Everything lands in the editable RFx editor.

**Ingestion router** (`router.py`, Haiku): file → {format, parser, needs_vision: bool, pages/sheets to read, language}. Also splits multi-item emails into candidate line mentions.

**Extraction agent** (`extractor.py`): per file, per model. Input: parsed text with layout hints, or page images; RFx line list with specs (for matching hints only). Output: `Extraction[]` with strict schema. Rules: quote the verbatim snippet for every value; never convert units or currency; if a value is conditional (footnote, "freight extra," "rest same as last year") emit it as `condition` with the text, not as a number. Runs primary and secondary in parallel; the service computes agreement.

**Line matcher** (service plus Haiku tie-break): maps extracted rows to RFx lines by spec similarity (dims, ply, gsm) with a deterministic score; below threshold, Haiku proposes a match with reason; below a second threshold the row is flagged `unmatched`.

**Normalization** (service, no LLM): raw_value × unit factor × pack factor × FX → `inr_per_base`. Factors come from `conversion_table.yaml` (admin-editable in Settings). Ambiguous units (`box`, `bundle`, `set`) produce a `unit_ambiguity` ReviewItem with each interpretation computed. ₹/kg quotes use `board_weight_kg_per_pc` from the RFx spec and record it in the trace.

**Validation** (service): 27-of-30 detection, outliers (>2σ from line median flagged with reason), currency mismatch, missing freight statement, conditional discounts not yet applied, model disagreement > tolerance (numeric tolerance 0.5%).

**Evaluation agent** (`evaluator.py`): questionnaire answers plus attachments → per-question pass/fail/unanswered with evidence snippet; vendor result = Pass if all mandatory pass, Partial if any unanswered, Fail if any mandatory fail. Evaluator persona can override with reason.

**Analyst agent** (`analyst.py`): question plus DuckDB schema plus the assumptions in force → {plan, sql_or_pandas, explanation}. The service executes the code in a sandboxed subprocess with a timeout against the `confident`-only view (plus overrides), returns rows, then the agent writes the answer from the rows. Rules: the answer must state which lines are excluded and why; charts are generated from the result rows; the executed query is returned and shown. If the question cannot be answered from the grid, say so and suggest what data would be needed.

**Clarification agent** (`clarifier.py`): ReviewItem(s) → a vendor email draft with the exact ambiguity, the options, and a reply format. Written to outbox. Never sent automatically.

**Award engine** (service): scenario → allocations by rule (lowest normalised per line, eligibility filter, single-source cap optional), exclusions with reasons, cost of each rule versus unconstrained, open items that block approval.

## 7. Dataset spec (`data/gen/`)

Generate with scripts, commit the outputs. Use realistic Indian corrugated pricing (₹ per 1,000 pcs, roughly ₹6k for edge protectors up to ₹1.2 L for 7-ply export cartons). Vendors, replies, and their deliberate breakage:

| Vendor | Format | Breakage |
|---|---|---|
| Meridian Packaging | .xlsx, own layout, merged header cells, prices in a second sheet | Ignores the template; column named "Rate" with unit in a note cell |
| Sri Balaji Corrugators | .pdf on letterhead, 3 pages | 4% discount buried in footnote 2 with a condition ("lines above ₹1 L") |
| Kaveri Boards | .docx, commercials in prose paragraphs | Quotes USD; L01 "per box" with "packed 100 per bundle" in the same sentence; 29 of 30 lines |
| NorthBox Ltd | .jpg photo of a printed rate card, 14° skew, slight blur | 27 of 30 lines; one digit legitimately ambiguous; fails a mandatory questionnaire item |
| Anand Papers | .eml, two lines of text | "₹42/kg for the 5-ply, 38 for the 3-ply, rest same as last year, freight extra" |

The golden set (`data/golden/*.json`) is written by the same generator, so truth is exact. Questionnaire: 8 questions, 3 mandatory (BRC or equivalent certification, food-contact ink compliance, minimum 2 production sites). Attachments: 3 files, one per vendor that supplies one.

## 8. Evaluation harness (`app/eval/`)

`make eval` runs extraction on all five replies with primary and secondary models, compares to golden, and prints and stores: per-field accuracy per vendor per model, agreement rate, flagged-precision (how many flags were real problems), missed-problem count, mean latency and cost. The JUDGE model grades free-text fields (conditions, freight statements). The report is linked from the Run inspector and its headline numbers go in the note.

## 10. Build order with gates

Build in this sequence. Each checkpoint is a hard gate: do not start the next block until it passes. No clock: move as fast as the gates allow.

1. Repo scaffold, tokens, Makefile, schemas, LLM clients with tracing. **Checkpoint A:** one traced call to each of the three providers succeeds.
2. Dataset generators and golden set. **Checkpoint B:** `make seed` produces the RFx and the five reply files; golden JSON matches the generators; every file opens in its native app.
3. Ingestion router, parsers, extraction agent (dual model), line matcher. **Checkpoint C:** all five replies extract; Meridian and Sri Balaji at 100% on golden; Kaveri, NorthBox and Anand raise their expected flags. This is the gate that proves the AI loops are real.
4. Normalization, validation, review items, grid endpoint. **Checkpoint D:** `GET /grid` returns 150 cells with correct states; totals exclude flagged and not-quoted lines.
5. Compare screen and provenance popover.
6. Review queue screen with resolve, override and ask-vendor flows, all audited.
7. Analyst agent, sandboxed executor, Analyse screen with query display, chart and export. **Checkpoint E:** the VP's split-award question and five unrehearsed questions answer correctly against golden-derived truth.
8. Award engine and screen; evaluator agent and questionnaire strip; Responses and Draft screens.
9. `make eval`, Run inspector, Settings, dark theme pass. **Checkpoint F:** `make demo` on a fresh clone reaches Compare in under 5 minutes.
10. Record the walkthrough (`docs/WALKTHROUGH.md`: 8 to 10 minutes; the VP question, one ambiguity resolution, one question the system refuses, one export).
11. Write `docs/NOTE.md` (one page) and finish `docs/DESIGN.md`.
12. Fresh-clone test, final push, submission.

If you run short, cut from the bottom of the screen list in section 9 (Settings, Sent, Draft polish), never from non-negotiables 1 to 8, and never from steps 10 to 12.

## 12. Deliberately out of scope (say so in the note)

Real email transport and vendor portal; multi-currency beyond one foreign vendor; contract terms extraction; ERP or PO integration; multi-tenant auth (persona switcher stands in); scanned-volume OCR pipeline (production path named); negotiation rounds; approval workflows beyond one approver.

## 13. How to work with Claude Code on this

- Start each session by reading this file, then `docs/DESIGN.md`, then the checkpoint you are on.
- Build vertically: schema → service → endpoint → test → screen, one feature at a time. No screen before its endpoint returns real data.
- Write the test that reads the golden set before writing the extractor.
- Commit at every checkpoint with the checkpoint letter in the message.
- When tempted to hardcode anything for the demo, write it down in `docs/NOTE.md` under "things I refused to fake" instead.
